# Image-storage feasibility audit (2026-10-19)

## Decision

Do not run a blind image-storage A/B as a proposed way to accelerate the hot 64→64 Winograd GEMM. On the supplied Adreno 740 capability report, the Winograd intermediate image width is over `maxImage3D=2048`; pinned ncnn 20241226 therefore marks those convolution layers as not supporting image storage and uses the VkMat/buffer forward path. Image loads do compile to `texelFetch` on eligible image pipelines, so texture-cache use is plausible for other eligible layers, but the target GEMM cannot use that path at these dimensions. This is a static rejection of image storage for the hot GEMM path, not a claim that every layer or workload is ineligible.

## Evidence and dimensions

`device-gpu-caps-20261019.json` reports `type=1`, `subgroupSize=64`, `maxImage3D=2048`, `maxImage2D=16384`, `storageBufferNoL1=true`, `imageLoadZeroBug=false`, and `cooperativeMatrix=false`.

For the Native x2 convolution tensor under review, the input is 420×420 and the model's 3×3 Convolution layers set parameter `4=1` (symmetric pad 1). The saved pilot parameter snapshot `fused-1.param` contains 18 Convolution entries and every entry has `4=1`; `fused-1.json` identifies it as derived from the frozen native2 head3 assets. In pinned `Convolution::load_param`, parameter 4 initializes `pad_left`, and absent parameters 15, 14, and 16 default `pad_right`, `pad_top`, and `pad_bottom` from it (`src/layer/convolution.cpp:38-41`). Vulkan shape setup adds left/right padding to the input width (`convolution_vulkan.cpp:68-75`), producing bordered width 422; with a 3×3 stride-1 convolution, the output width remains 420. Winograd43 uses `ceil(out/4)` blocks on each axis and stores their product as transformed tensor width (`convolution_vulkan.cpp:340-344,352`): `105×105 = 11,025`. Winograd23 uses `ceil(out/2)` (`:618-622,630`): `210×210 = 44,100`. For the pack4 64-channel case the transformed tensors are width `11,025` or `44,100`, height 16, and depth 36 for Winograd43 (depth 16 for Winograd23). The width alone exceeds the device's 3D image limit by 5.4× or 21.5×.

`gpu.cpp:3493-3525` checks each 3D image dimension against `max_image_dimension_3d()` and returns false when any dimension is too large. The Winograd setup then sets `support_image_storage=false` and disables image storage for that layer when either transformed input/output or packed weights fail the shape check (`convolution_vulkan.cpp:352-363,630-641`). The target 64→64 GEMM consequently remains a buffer pipeline even if the network option requests images. `storageBufferNoL1=true` motivates testing a different access pattern, but it does not remove this image-dimension fallback.

The read-only image path is real for eligible layers: the shader declares image operands and uses `image3d_ld4`; pinned `gpu.cpp:4284-4287` maps that load to `texelFetch` and stores to `imageStore`. This gives eligible reads a sampled-texture path, but source inspection cannot establish cache hits or a speedup. The reported `imageLoadZeroBug=false` removes that particular device limitation; it does not change the maximum image dimension.

## Extractor and fallback cost

The existing `Extractor::extract(..., VkMat&, ...)` path at `net.cpp:2900-2928` materializes a VkMat and calls the buffer-only forward path when it has to run a producer. It does not establish an end-to-end VkImageMat path for measuring image storage. A harness intended to exercise images must use `Extractor::input(blob, VkImageMat)` and `Extractor::extract(blob, VkImageMat&, cmd)` (`net.cpp:2940-2994`) so eligible layers retain image-backed blobs through the graph.

Even with that harness, `NetPrivate::forward_layer` converts an image bottom to a buffer for an unsupported layer, and converts a buffer bottom back to an image for an image-supported layer (`net.cpp:411-477,545`). PReLU declares image-storage support (`prelu_vulkan.cpp:24`). Thus an unsupported Winograd convolution between image-capable layers can introduce image→buffer and buffer→image transitions at its boundaries; adjacent unsupported convolutions can share the buffer interval. The exact count depends on the loaded graph. No conversion timing or full-graph image run was done here, so the net cost is unknown, but the hot Winograd GEMM itself would still not sample from an image.

If image storage is revisited for a different eligible graph, the minimum isolated harness change is to retain VkImageMat for both Vulkan input and output, then record per-layer image eligibility and image↔buffer transitions. First require bitwise-equal float output and zero differing RGB values against the same stock model/input; only then compare warmed full-run medians on the Adreno. For the stated 420×420 padded x2 graph, these checks do not justify an image-toggle experiment for the hot GEMM because its shape is statically ineligible.

## Targeted shared-memory GEMM follow-up

The independent targeted override keeps the integrated-GPU/global option false and enables shader local memory only on the guarded 64→64, pack4, buffer, FP16-storage/FP32-arithmetic GEMM pipeline; its local size is 8×8×1. It uses the shader's existing `shared tmp_v`/`tmp_k` arrays and workgroup barriers (`convolution_pack4_3x3s1d1_winograd_gemm.comp:56-58,101-193`). The 8×8 local x/y extents match the arrays' first dimensions. For 64→64 pack4, output packs are 16 (divisible by local y=8), input packs are 16 (two complete unroll groups of 8), and local z=1, so the target's y/z work is fully covered.

There is an x-tail hazard in the upstream shared branch: `gx` advances four spatial entries per invocation, while the bounds return occurs only after the shared loads and barriers (`shader:63-70,108-124,152-172,220-223`). With width 11,025, the last valid invocation has `gx=11,024` and only its first of four loaded entries is valid; rounded workgroups also create later invalid x invocations. The isolated candidate patch protects both shared `tmp_v` loads by clamping the per-lane x index to `outw-1` (`shared-gemm.patch`, both hunks). For valid entries this index is unchanged; invalid x lanes still reach every barrier, then return before stores. With the target's divisible output-channel count, the corresponding `tmp_k` load has no y-tail. This addresses the identified partial-x read risk for the guarded target geometry.

The Adreno pilot then rejected the route on speed. In `gemmshared-pilot-20261019T121742.private/report.json`, the 400×400 color case had 32 candidate markers, global effective local memory remained false, and image storage and FP16 arithmetic remained off. The stock/rebuilt control was 252.18 ms and the shared candidate was 351.34 ms (`-39.32%`); CPU time was 26.36 ms versus 26.44 ms. Float and RGB outputs were exact (`floatDifferentValues=0`, `rgbDifferentValues=0`). Exactness passes, but the required ≥5% speedup gate fails decisively. Keep this experiment out of the app and stop this parameter path; the pilot is an isolated tensor/model result, not a full reader or energy measurement.

This audit read source, capability JSON, patch, and saved pilot results only. It did not edit code, build, or run a device test. No file other than this audit was changed.
